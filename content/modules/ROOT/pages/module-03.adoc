=== Custom Resource Monitor Creation

Let’s configure a custom disk resource monitor and apply it to our fleet. To do so, we will use the `flightctl` CLI.

Return to your lab manual and input the following commands in `Terminal 1`

.Retrieve the fleet list
[source,sh,role=wrap execute,subs=attributes+]
----
flightctl get fleet
----
.Sample Output (returns all fleets)
[source,text,role=wrap]
----
NAME            OWNER   SELECTOR        VALID
drone-fleet     <none>  fleet=lab       True
----
.Export the `drone-fleet` configuration to YAML
[source,sh,role=wrap execute,subs=attributes+]
----
flightctl get fleet/drone-fleet -o yaml > update-fleet.yaml
----
.Edit the update-fleet.yaml file
[source,sh,role=wrap execute,subs=attributes+]
----
vim update-fleet.yaml
----

. While reviewing the `spec:` section, note that this fleet specification now defines:
* An *application* (`drone-cam-app`)
* A *host configuration* source (`update-motd`)
* A *systemd service* that must be present and running (`chronyd.service`)
+
Together, these entries define the desired state that Edge Manager continuously enforces for every device that matches this fleet.
+
image::m3-monitor-1.png[link=self, window=blank, width=100%]
+
. Use the down arrow key to position your cursor on the `status:` line
. Press `i` to enter insert mode
. Press `Enter` to create a new blank line
. Press the up arrow once to move your cursor into the empty line above `status:`
+
image::m3-monitor-2.png[link=self, window=blank, width=100%]
+
[source,sh,role=execute,subs=attributes+]
.Copy the following custom disk resource monitor YAML:
----
      resources:
      - monitorType: Disk
        samplingInterval: 5s
        path: /sysroot
        alertRules:
        - severity: Warning
          duration: 1m
          percentage: 5
          description: Disk space for /sysroot is >5% full for over 1m.
        - severity: Critical
          duration: 10m
          percentage: 90
          description: Disk space for /sysroot is >90% full over 10m.
----
. Paste this YAML snippet directly above the status: field in the fleet specification
. Press `ESC` to exit insert mode
. Type `:wq` and press `Enter` to save and exit the file
+
We have saved our modification, now let's apply it:
+
[source,sh,role=wrap execute,subs=attributes+]
.Type or copy/paste the following command
----
flightctl apply -f update-fleet.yaml
----
+
.Sample Output (returns all fleets)
[source,text,role=wrap]
----
update-fleet.yaml: applying fleet/drone-fleet: 200 OK
----

While we wait for this to fully apply, let's examine what this custom disk resource monitor is doing:

image::m3-monitor-3.png[link=self, window=blank, width=100%]

. Specifies a `monitorType: Disk` and samples disk utilization on the `/sysroot` path every `5s`
. Triggers a *Warning alert* if disk usage on `/sysroot` exceeds *5% for longer than 1 minute* (5% disk usage is not a realistic (real world) value; we're simply using this in order to generate an alert notification)
. Triggers a *Critical* alert if disk usage on `/sysroot` exceeds *90% for longer than 10 minutes*, which more closely reflects a realistic production threshold.

=== Observability

NOTE: In addition to Events and Alerts, Edge Manager supports Observability capabilities for device and service *metrics, profiling, tracing, and audit logs*. This data can be stored over time to enable historical analysis and long-term insights.

Configuring Observability is beyond the scope of our lab; however, at a high level the following describes this functionality and flow: +

* Uses OpenTelemetry Collector on a device and forwards collected data to the Telemetry Gateway +
* Telemetry Gateway saves collected data from devices and service, or forwards data to external Collector +
* Standalone observability stack is available for Edge Manager on RHEL and/or the Observability stack in OpenShift can be utilized

=== Desired State Configuration: Why It Matters

Imagine that you have been asked to change the title of the Drone Tracker application.  

A junior administrator (or even an experienced operator with decades of muscle memory might go directly to device and edit the web content in place). Let's follow that approach:

. Return to the Device *Terminal* in the Edge Manager UI
+
.Change into the `/etc/drone-tracker` directory
[source,sh,role=wrap execute,subs=attributes+]
----
cd /etc/drone-tracker
----
+
.Open `index.html' for editing
[source,sh,role=wrap execute,subs=attributes+]
----
vi index.html
----
+
. Navigate to '*<h1>SliceOps Delivery Systems* ...</h1>' line and press `i` for insert 
+
. Replace `SliceOps Delivery Systems` with any company name of your choosing
+
. Press *ESC*, then type `:wq` and press *Enter* to save the file 
+
. Return to your `Drone Tracker` browser tab, click *Back to Tracker Map* and refresh the page

Notice that the page header now reflects the company name you entered. The change was successful and is immediately visible in the Drone Tracker application.

So what’s the problem with this approach?

*Ask yourself this*: was this change made through the correct *desired state configuration* for the device?

*Answer*: No, it was not.

In fact, within a few minutes, you’ll notice the change automatically reverts back to *SliceOps Delivery Systems Drone Tracker*.

This happens because the device agent periodically checks in and evaluates whether its current state matches the desired state. When it detects a mismatch, Edge Manager automatically works to self-heal the device back to the declared configuration.

This is a powerful capability. Device self-healing can save organizations significant time and money by reducing manual intervention and avoiding costly truck rolls to remote edge locations. Edge Manager becomes the first line of remediation.

The correct approach in this case would have been to edit the gitea content and let the Fleet Specification (desired state configuration) do the rest.
