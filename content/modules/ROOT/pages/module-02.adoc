= 2. Edge Manager - Onboard

Now that Edge Manager is installed, we’ll focus on onboarding and managing your delivery drone edge device. The first step is creating an Image Mode (bootc) image.

== Edge Device Onboarding Workflow

image::m2-onboard-overview.png[link=self, window=blank]

We build the bootc image using standard Podman tooling (Podman and a Containerfile). Once the container image is built, we use `bootc-image-builder` to convert it into a bootable disk format such as ISO, QCOW2, or VMDK.

In most real-world deployments, this image would be written to removable media and installed on physical edge hardware. In this lab, we use an OpenShift Virtualization virtual machine to represent the delivery drone, so we’ll create a QCOW2 disk image.

image::m2-device-pre-reqs.png[link=self, window=blank]

To onboard a device, Edge Manager requires the following prerequisites:

. `Edge Manager Agent`: The device agent uses a pull-based architecture to retrieve configuration and updates, which is well suited for edge environments where inbound connectivity may be limited
. `Image Mode (bootc) image`: In this lab, we’ll build our own image. As shown in the illustration, a Containerfile is used to define the image contents
. `Enrollment Configuration`: This configuration file contains the information required for the device to enroll and authenticate with Edge Manager

== Edge Manager Architecture
Edge Manager consists of the following core components, illustrated in the high-level architecture diagram below:

image::m2-edge-manager-architecture.png[link=self, window=blank, width=100%]

. *Edge Manager Service* consists of an API server, background worker processes (not shown), and a PostgreSQL database. The database stores inventory and runtime state, including desired (target) device configuration and reported actual device configuration.
. *User access* is provided through two primary interfaces: the Edge Manager Web UI and the Edge Manager CLI.
. *Edge Device access* utilizes an Agent that is running on each managed device. The agent always calls home using a *pull-based model*, allowing devices to operate on private networks or with dynamic IP addresses. This model supports devices located behind NAT, firewalls, or connected via cellular or WLAN uplinks.
. *Git repository integration* (optional) enables storing desired device and fleet configuration as code. We will explore Git integration in an upcoming lesson.
. *External systems* are integrated by the Edge Manager service to perform authentication and authorization and retrieve configuration for managed devices.

Together, these components enable Edge Manager to centrally manage fleets of edge devices using a secure, pull-based, GitOps-friendly architecture.

=== Edge Manager Fleets

An Edge Manager fleet is a logical grouping of devices that share a common *desired state* and management policies. Fleets simplify large-scale operations by allowing administrators to define a single *fleet specification* that applies consistently across all devices in the group. This specification can include applications, host configuration, and OS image references, ensuring predictable behavior and updates across the fleet.

NOTE: A device can belong to at most one fleet at a time. This design avoids configuration conflicts and ensures each device has a single, authoritative source of truth for its desired state.

image::m2-fleet-definition-2.png[link=self, window=blank, width=100%]

Fleets provide centralized, template-driven management for groups of edge devices. Without centralized management, each device must be updated, monitored, and managed individually (an approach that is time-consuming and prone to inconsistency). 

With Edge Manager fleet management, a single fleet template defines the desired application set, host configuration and OS image for all member devices. This enables administrators to apply updates consistently, enforce configuration, and monitor fleet-wide health from a single point of control. Fleet status views summarize how many devices are healthy, updating, or in a failed state, enabling quick operational insight.

. Creates a temporary web server (http container)
. Ensures OpenShift is ready to receive the image (we'll need `oc credentials` for this in a moment)
. Triggers a DataVolume import into OpenShift-Virtualization so that it can be utilized by a new OCP-Virt Drone Virtual Machine that you will create

This terminal session may _look_ like an SSH connection, but it is not one.
+
Instead of connecting directly to the device over SSH, Red Hat Edge Manager provides terminal access using an mTLS-encrypted gRPC tunnel over HTTPS (port 443).
+
image::m2-gRPC-tunneling.png[link=self, window=blank, width=100%]
+
Traditional remote access to edge devices often relies on SSH over port 22.
This approach introduces several challenges at scale:
+
* NAT traversal and port forwarding requirements
* Static IP dependencies
* Firewall rule management
* SSH key distribution and rotation
* Limited scalability as device counts grow
+
[NOTE]
.Remote access architecture
====
Edge Manager provides remote access using outbound, mTLS-secured gRPC streams over port 443.

By avoiding inbound SSH access, this approach reduces firewall complexity, improves security, and enables scalable, centralized access across large device fleets.
====
